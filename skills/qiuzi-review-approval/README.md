# Qiuzi Review Approval

## 用途

`qiuzi-review-approval` 用于处理已经收到的 Code Review 意见。它会先逐条核查审查意见是否准确，剔除误报、合并重复意见，再给出受限的修改方案；只有收到用户明确确认后才会修改代码。

该 Skill 不用于从零开始审查代码，也不用于直接开发新功能。

## 使用方法

在 Codex 中直接说明 Review 意见，或显式调用：

```text
$qiuzi-review-approval
请核查以下 Code Review 意见，先给出修改方案，等待我确认后再改代码：
1. ...
2. ...
```

也可提供合并请求评论、截图文字、评审文档链接或已整理的意见清单。应尽量附带相关文件、行号、提交记录或预期行为，方便核查。

## 工作流程

1. **验证 Review**
   - 逐条核查实际代码与调用链；
   - 剔除误报；
   - 合并重复意见；
   - 标记证据不足项；
   - 输出最终确认的问题清单。
2. **制定修改方案**
   - 为每个确认问题给出推荐方案；
   - 有必要时列出替代方案及优缺点；
   - 明确修改范围与不处理项。
3. **等待确认**
   - 固定输出五种确认方式；
   - 在用户明确回复前不修改任何代码。
4. **实施修改**
   - 仅修改已确认的问题；
   - 禁止重构、风格优化、新增功能和无关文件改动；
   - 完成后不执行 `git add`、提交或推送。

## 示例

### 输入

```text
$qiuzi-review-approval
请核查以下 Review：

R1：src/order.ts:42 未校验 orderId，可能导致空值请求。
R2：src/order.ts:42 应把函数改为 async/await。
R3：src/order.ts:42 未校验 orderId，可能导致空值请求。
```

### 预期行为

Skill 会验证 R1、R2、R3：若 R1 与 R3 指向同一根因，则合并为一个确认问题；若 async/await 只是风格建议且不影响正确性，则不会将 R2 擅自纳入修改范围。随后输出方案与“等待确认”选项，并停止。

### 确认示例

```text
【1】全部采用推荐方案
```

或：

```text
【5】只处理 P1，采用推荐方案；不要修改其他文件。
```
